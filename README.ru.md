# proctun

**Пер-процессный split tunneling для Windows.** Выбранные приложения
направляются через OpenVPN-туннель, а остальные продолжают пользоваться
обычным подключением — либо наоборот: через туннель идёт всё, кроме
приложений, перечисленных в правилах.

proctun работает поверх любого OpenVPN TAP-туннеля, целиком в user mode,
через подписанный драйвер
[WinpkFilter](https://github.com/wiresock/ndisapi). Один исполняемый файл
служит и CLI, и службой Windows.

[English version](README.md)

```console
$ proctun status

  proctun 0.3.7

  SERVICE
    state            running
    engine           exclude/full-tunnel
    tunnel           up ✔
    wan              Wi-Fi  192.168.1.10
    tun              OpenVPN TAP  10.8.0.6

  COUNTERS
    tunneled         48210
    dns              377
    killed           0

  CONFIG
    mode             exclude
    leakguard        on
    ...

  RULES (1)  exclude mode — matched processes bypass the tunnel
    chrome.exe        → direct
```

## Возможности

- **Маршрутизация по процессам** — правило сопоставляется с именем
  исполняемого файла или любой частью его полного пути.
- **Две политики** — `include` (туннель используют только перечисленные
  приложения) и `exclude` (туннель используют все приложения, кроме
  перечисленных).
- **Совместимость с существующей конфигурацией VPN** — proctun подстраивается
  под то, как уже настроен туннель (см.
  [Стратегии маршрутизации](#стратегии-маршрутизации)), и никогда не изменяет
  таблицу маршрутов самостоятельно.
- **Защита от утечек** — DNS направляется в туннель, IPv6 туннелируемых
  приложений блокируется, а kill switch при падении туннеля дропает трафик,
  а не выпускает его наружу.
- **Собственного кода в ядре нет** — всё исполняется в user mode поверх
  стороннего подписанного драйвера.

## Требования

- Windows 10/11 x64 и права администратора (доступ к драйверу и службам).
- OpenVPN на L2 TAP-адаптере: `dev tap` и `disable-dco`. Wintun и DCO работают
  на L3 и не поддерживаются — WinpkFilter требуются Ethernet-кадры.
- Драйвер WinpkFilter 3.6.2 или новее, устанавливается командой
  `proctun init`.

## Установка

Из PowerShell с правами администратора:

```powershell
.\proctun.exe init
```

Команда копирует исполняемый файл в `%ProgramFiles%\proctun`, добавляет этот
каталог в системный PATH (чтобы `proctun` был доступен в любой новой консоли)
и устанавливает драйвер ядра WinpkFilter. MSI скачивается из GitHub-релиза
вендора и проверяется по SHA-256-пину и Authenticode-подписи; продолжение
после запроса означает принятие
[лицензии вендора](https://www.ntkernel.com/windows-packet-filter/). На машине
без доступа в интернет локальный установщик передаётся через
`--driver-path <msi>`.

Проверка:

```powershell
proctun ndis      # ✔ WinpkFilter driver loaded
```

## Быстрый старт

Сначала должен быть поднят VPN — proctun привязывается к адаптерам в том
состоянии, в котором они находятся на старте движка. Далее в консоли с
правами администратора выполняется следующее:

```powershell
# туннель используют только эти приложения
proctun set --mode include --tun-gw 10.8.0.1
proctun add chrome.exe

proctun up -d      # запуск фоновой службой
proctun status     # tunnel ✔ и растущие счётчики говорят о штатной работе
proctun down       # остановка
```

Обратный сценарий — через туннель идёт всё, кроме одного приложения:

```powershell
proctun set --mode exclude --tun-gw 10.8.0.1 --tunnel-remote 203.0.113.10
proctun add SomeApp.exe
proctun up -d
```

Два значения берутся из VPN-сессии:

| Значение | Источник | Опция |
|---|---|---|
| Шлюз туннеля | `route-gateway 10.8.0.1` в логе OpenVPN | `--tun-gw` |
| IP VPN-сервера | `remote <ip> <port>` в файле `.ovpn` | `--tunnel-remote` |

Результат проверяется открытием страницы «what is my IP» в перенаправленном
приложении: оно показывает адрес VPN, тогда как любое другое приложение —
настоящий.

`proctun up` **без** `-d` держит движок в форграунде с живыми логами и
остановкой по Ctrl+C — это удобный способ отладки настройки.

## Стратегии маршрутизации

proctun на старте читает таблицу маршрутов и подстраивается под то, как
настроен VPN. Стратегия не выбирается вручную; активную показывает `status`.

| Конфигурация VPN | Стратегия | Поведение движка |
|---|---|---|
| Маршрут по умолчанию остаётся на физическом канале (`route-nopull`, без `redirect-gateway`) | **classic** | Нужный трафик заталкивается *в* туннель |
| `redirect-gateway def1` — ОС и так отправляет всё в туннель | **full-tunnel** | Трафик, которому положено идти напрямую, вытаскивается *из* туннеля |

Стратегия фиксируется на старте движка. После переподключения VPN с другими
опциями proctun требуется перезапустить (`down`, затем `up`); в лог пишется
предупреждение, когда движок замечает, что маршрутный мир изменился.

## Команды

`proctun [-v] [--config <путь>] <команда> [аргументы]` — одна команда за
вызов, всегда с правами администратора.

| Команда | Описание |
|---|---|
| `init [--yes] [--force] [--driver-path <msi>]` | Разовая подготовка машины: alias в PATH и установка драйвера. Идемпотентна |
| `up [-d] [опции]` | Запускает движок в форграунде или, с `-d`, фоновой службой |
| `down` | Останавливает службу и снимает весь перехват |
| `status` | Состояние службы, живые счётчики, конфигурация и правила |
| `add <match> [--via] [--dns]` | Добавляет правило. `--via` и `--dns` зарезервированы и пока ни на что не влияют |
| `remove <match>` | Удаляет правила, чья маска в точности равна заданной строке |
| `list` | Выводит текущие правила |
| `set [опции]` | Изменяет и сохраняет настройки, затем выводит `status` |
| `leakguard <on\|off>` | Сокращение для `set --leakguard` |
| `adapters` | Перечисляет адаптеры и отмечает выбранный в качестве WAN |
| `ndis` | Состояние драйвера и интерфейсы его глазами (GUID'ы, индексы) |
| `sniff <индекс> [--seconds N]` | Пассивный захват на одном интерфейсе; ничего не изменяет |
| `install` / `uninstall` | Регистрирует или удаляет службу Windows |
| `update` | Разворачивает запущенный исполняемый файл поверх установленной копии и перезапускает службу |

### Опции

Принимаются командами `set` и `up`. `set` и `up -d` сохраняют значения в
конфигурацию, тогда как форграунд-`up` применяет их только к текущему
запуску. Непереданные опции сохранённые значения не изменяют.

| Опция | По умолчанию | Значение |
|---|---|---|
| `--mode <include\|exclude>` | `include` | Какая сторона правил пользуется туннелем |
| `--tun-gw <ip>` | — | Шлюз туннеля (OpenVPN `route-gateway`) |
| `--tunnel-remote <ip>` | — | IP VPN-сервера, никогда не туннелируется. Обязателен для `exclude` при стратегии classic |
| `--dns <ip>` | `1.1.1.1` | Резолвер, в который перенаправляется весь DNS; должен быть достижим через туннель |
| `--tun <guid\|имя>` | авто | Закрепляет TAP-адаптер |
| `--wan <guid\|имя>` | авто | Закрепляет физический адаптер |
| `--leakguard <on\|off>` | `on` | Общий выключатель для двух настроек ниже |
| `--ipv6-block <on\|off>` | `on` | Дропает IPv6 туннелируемых процессов |
| `--tunnel-dns <on\|off>` | `on` | Направляет весь DNS в туннель |

### Выбор адаптеров

Оба адаптера определяются автоматически: **WAN** — по истинному маршруту
`0.0.0.0/0` (активный redirect-gateway определение не сбивает), **TUN** — как
первый поднятый TAP-адаптер с IPv4-адресом. В выводе `proctun adapters`
пометка `◀ wan` должна стоять на физическом адаптере (Ethernet/Wi-Fi), причём
поднятым должен быть только предполагаемый туннель.

Если другой VPN держит второй TAP-адаптер, оба адаптера можно закрепить по
GUID:

```powershell
proctun ndis                              # покажет GUID'ы
proctun set --wan "{...}" --tun "{...}"
```

`--tun-gw` должен принадлежать подсети самого TUN-адаптера: шлюз от чужого
туннеля даёт кадры, уходящие в никуда, и в этом случае proctun отказывается
стартовать.

## Конфигурация

`%ProgramData%\proctun\config.json` общий для CLI и службы. Правку через
`set`/`add`/`remove` следует предпочесть ручному редактированию: битый файл
отвергается с сообщением, и вместо него используются значения по умолчанию.
Изменения вступают в силу при следующем старте движка.

```jsonc
{
  "mode": "include",                  // "include" | "exclude"
  "rules": [
    { "match": "chrome.exe", "via": "tun" }
  ],
  "tun_gateway": "10.8.0.1",        // шлюз туннеля (route-gateway)
  "tunnel_remote": "203.0.113.10",  // IP VPN-сервера
  "tun_alias": "",                  // GUID/имя TAP-адаптера ("" = авто)
  "wan_alias": "",                  // GUID/имя WAN-адаптера ("" = авто)
  "leakguard": true,
  "block_ipv6": true,               // дропать IPv6 туннелируемых процессов
  "tunnel_dns": true,               // перенаправлять весь DNS в туннель
  "dns_server": "1.1.1.1"
}
```

| Путь | Назначение |
|---|---|
| `%ProgramData%\proctun\config.json` | Конфигурация |
| `%ProgramData%\proctun\stats.json` | Живая статистика, обновляется примерно раз в секунду |
| `%ProgramData%\proctun\proctun.log` | Лог службы |
| `%ProgramFiles%\proctun\proctun.exe` | Установленная копия (`init`) |

Служба Windows: `proctun`, LocalSystem, ручной запуск.

## Скриптование

proctun сознательно не управляет OpenVPN. Предполагается его запуск внешним
скриптом после того, как TAP-адаптер получил IP-адрес, и остановка, когда VPN
уходит:

```powershell
proctun up -d      # VPN поднят
proctun down       # VPN опускается
```

`stats.json` машиночитаем и обновляется примерно раз в секунду:

```powershell
Get-Content "$env:ProgramData\proctun\stats.json" | ConvertFrom-Json
# .armed, .mode, .tunneled, .dns, .killed, .conntrack, .tun_ip, ...
```

## Устранение неполадок

| Симптом | Решение |
|---|---|
| `WinpkFilter driver NOT loaded` | Выполнить `proctun init` |
| `could not resolve adapters` | Туннель лежит или отсутствует TAP-адаптер — поднять VPN либо закрепить `--tun`/`--wan` по GUID |
| `WAN resolved to the tunnel adapter` | Автовыбор или устаревший alias выбрал не тот адаптер — задать `--wan` по GUID физического адаптера |
| `could not resolve MAC of tunnel gateway` | Ещё нет ARP-записи: однократный `ping <tun-gw>`, затем повтор |
| `exclude mode requires tunnel_remote` | Задать `--tunnel-remote <IP сервера>` |
| `strategy is stale` в логе | VPN изменил таблицу маршрутов после старта — `down`, затем `up` |
| Служба не стартует по `up -d` | Обратиться к `%ProgramData%\proctun\proctun.log` либо запустить `proctun up -v` в консоли |
| У перенаправленного приложения нет сети | В `status`: поднят ли туннель, верен ли `tun-gw`, попадает ли приложение под правило (`list`)? |
| DNS перестал резолвиться | Попробовать `set --tunnel-dns off` либо проверить достижимость `dns_server` через туннель |
| Сразу после старта ничего не работает, туннелируются не те приложения | Вероятнее всего выбраны не те адаптеры — см. [Выбор адаптеров](#выбор-адаптеров) |

## Как это работает

proctun переводит адаптеры WAN и TAP в NDIS tunnel mode, благодаря чему
каждый Ethernet-кадр проходит через движок в user mode. Маршруты никогда не
добавляются и не удаляются — вместо этого переписываются и перенаправляются
отдельные пакеты.

<details>
<summary><b>Путь пакета</b></summary>

**classic** — ОС отправляет всё через физический канал:

```
  пакет на WAN ──▶ туннелировать? ──да──▶ SNAT ──▶ TAP (в VPN)
                                  └─нет──▶ пропустить как есть
  ответ на TAP ──▶ DNAT ──▶ отдан сокету процесса
```

Пакету, который необходимо туннелировать, переписывается IP источника на
адрес TAP-адаптера и собирается новый Ethernet-заголовок (адресат — MAC шлюза
туннеля, резолвится один раз через ARP), после чего кадр реинжектится в TAP.
Порты не изменяются, поэтому общий connection tracking не требуется.

**full-tunnel** — ОС и так отправляет всё в VPN, поэтому движок зеркалит себя:

```
  пакет на TAP ──▶ оставить напрямую? ──да──▶ SNAT ──▶ WAN (мимо VPN)
                                      └─нет──▶ пропустить как есть
  ответ на WAN ──▶ это известный поток? ──▶ DNAT ──▶ обратно в стек TAP
```

Родной для WAN трафик (транспорт самого VPN, LAN) должен оставаться
нетронутым, поэтому извлечённые потоки фиксируются в небольшой таблице
(протокол, порт), и обратной трансляции подвергаются только их ответы.
Исключения по адресам, установленные самим VPN-клиентом
(`route ... net_gateway`), продолжают работать без изменений.
</details>

<details>
<summary><b>Сопоставление процессов</b></summary>

WinpkFilter не сообщает, какому процессу принадлежит пакет. Движок определяет
это по таблицам соединений ОС (`GetExtendedTcpTable` / `GetExtendedUdpTable`:
локальный endpoint → PID → полный путь исполняемого файла, с кэшем и ленивым
обновлением при промахе) и сопоставляет путь с правилами как
регистронезависимую подстроку.

Пакет, чей процесс определить не удалось, в режиме `exclude` считается
туннелируемым (fail-closed), а в режиме `include` — идущим напрямую.
</details>

<details>
<summary><b>DNS и IPv6</b></summary>

Имена в Windows резолвит служба `dnscache`, поэтому DNS-трафик невозможно
привязать к запросившему приложению. При включённом `tunnel_dns` каждый
IPv4-пакет на порт 53 перенаправляется в туннель с подменой адресата на
`dns_server`; оригинальный резолвер запоминается по паре (протокол,
клиентский порт) и восстанавливается в ответе, поскольку иначе ОС его
отбросит. Размен состоит в том, что через туннель идёт DNS *всех* приложений.

Data path туннеля — только IPv4. IPv6-DNS дропается, чтобы резолверы
откатывались на IPv4; при включённом `block_ipv6` дропается и IPv6
туннелируемых процессов, из-за чего приложения повторяют попытку по
(туннелируемому) IPv4. IPv6 остальных приложений остаётся нетронутым.
</details>

<details>
<summary><b>Kill switch</b></summary>

Поток-монитор примерно раз в две секунды проверяет охраняемый адаптер — TAP
при стратегии classic, WAN при full-tunnel — на то, что тот поднят и сохраняет
IP-адрес, который был на старте движка. Пока адаптер лежит, трафик, который
должен был через него пройти, дропается, а не уходит по неверному пути:
стратегия classic дропает туннелируемый трафик, включая DNS, full-tunnel —
извлечённые прямые потоки, не давая им провалиться обратно в VPN. В `status`
это видно как `tunnel DOWN` и растущий счётчик `killed`.
</details>

## Ограничения

- Data path туннеля — только IPv4; IPv6 туннелируемых процессов блокируется.
- При включённом `tunnel_dns` через туннель идёт DNS всех приложений.
- Параметры адаптеров и стратегия маршрутизации фиксируются на старте движка,
  поэтому после реконнекта VPN, сменившего IP-адрес TAP-адаптера или таблицу
  маршрутов, требуется перезапуск.
- OpenVPN должен использовать `dev tap` и `disable-dco`.
- IP-фрагменты проходят без классификации (при нормальном MTU — редкость).

## Сборка из исходников

Visual Studio 2026 (toolset C++ x64), CMake 3.21 или новее, vcpkg.

```powershell
git clone <этот репозиторий> && cd proctun
git submodule update --init          # SDK WinpkFilter → vendor/ndisapi

$env:VCPKG_ROOT = "<путь к vcpkg>"
cmake --preset win-amd64-release-vs2026-ndis
cmake --build out\build\win-amd64-release-vs2026-ndis --config Release

.\out\build\win-amd64-release-vs2026-ndis\Release\proctun.exe update   # развернуть
```

Пресет `win-amd64-release-vs2026` (без `-ndis`) собирает всё, кроме пакетного
движка, что удобно для работы над CLI на машине без драйвера.

Зависимости через vcpkg: CLI11, spdlog, nlohmann-json, ms-gsl. User-mode SDK
WinpkFilter подключён сабмодулем; его драйвер ядра устанавливается отдельно
командой `proctun init` на условиях
[лицензии вендора](https://www.ntkernel.com/windows-packet-filter/).
